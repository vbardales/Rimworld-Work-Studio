## What was actually caught

This suite exists because of one real defect, found before it existed: `Source/WorkStudio.csproj`
declares `<Publicize Include="Assembly-CSharp" />` and `<GenerateAssemblyInfo>false</GenerateAssemblyInfo>`
together, the exact combination that silently dropped `Contented Livestock`'s waiver
(`rimworld-tests-hors-jeu`, "the mod publicises" chapter). `WorkStudio.dll` had the same hole:
the `IgnoresAccessChecksToAttribute` type was embedded but never applied. `PriorityMemory.Restore`
reads `Pawn_WorkSettings.priorities` and writes its `workGiversDirty`, both private in the real
game, on every `Apply()` — meaning every startup and every edit. Left alone, this was a
`FieldAccessException` waiting on the desktop CLR the first time any pawn's priorities were
restored; whether Mono in the shipped game enforces the same check was never established either
way in this codebase (see the same memory chapter's "severity not established" note), which is a
reason to fix it, not a reason to leave it.

Confirmed by mutation: removing `Source/AccessChecks.cs` and rebuilding turns two checks red with
a real `FieldAccessException` thrown from inside `PriorityMemory.Restore`. Restoring the file and
rebuilding turns them green again. Both runs are reproducible from a clean tree.

## The full scope, found by a real IL scan rather than assumed

A second check (`TheNonPublicMemberScan`) walks every method body the shipped DLL contains,
resolves every field/method token it references, and flags whichever belong to `Assembly-CSharp`
and are not public — the "balayage inverse" from `rimworld-tests-hors-jeu`. Manual reading of the
source had found four private members before this scan existed
(`Pawn_WorkSettings.priorities`/`workGiversDirty`/`CacheWorkGiversInOrder`,
`PawnColumnDef.workerInt`, `BackstoryDef.cachedDisabledWorkTypes`). The scan found **three more**,
all real and all already covered by the same one-line fix:

- `GenFilePaths.FolderUnderSaveData` — called directly by `ConfigFile.Folder`.
- `DefDatabase<T>.Remove` — called by `WorkTypeRuntime.SyncCustomTypes` to retire a deleted custom
  work type's `WorkTypeDef` and `PawnColumnDef`.
- `Pawn_WorkSettings.pawn` — read by `Patch_WorkSettingsExposeData.Restore` to notify the pawn
  after loading named priorities back.

Two more members are touched and correctly *not* flagged: `MainButtonWorker..ctor` and
`ModSettings..ctor`, both `protected` and reached only from a subclass declared in this mod
(`MainButtonWorker_OpenSettings`, `WorkStudioSettings`) — ordinary legal C# that needs no waiver at
all, per the same memory chapter's exemption rule. The check itself asserts the conditional form
that chapter settles on: finding non-public members here is expected, since the mod deliberately
uses the Publicizer; failing would mean finding them *without* the assembly declaring the waiver.

## TESTING.md scenario 7, proven off-game against the real third-party assembly

`WorkTypeTagCompat.Notify()` claims that [baku] Work Type Tag (Workshop 3779138895) caches a work
type's label the first time it draws it, keyed by the `WorkTypeDef` instance, and only clears that
cache from its own settings window — so a rename from Work Studio would leave the old name showing
in front of a colonist's current job until `InvalidateAll()` runs. `TheWorkTypeTagCompat` loads the
real `baku.WorkTypeTag.dll` from the local Workshop subscription (skips cleanly if not installed),
renames a `WorkTypeDef`, confirms the label really is stale before calling
`WorkStudio.WorkTypeTagCompat.Notify()` itself (not a reimplementation of it), and confirms the
label is current afterwards. Confirmed by mutation: corrupting the resolver type name
`WorkTypeTagCompat.cs` looks up turns the last of the three checks red; restoring it turns the
suite green again.

## TESTING.md scenario 11, proven off-game too, on a second look

First attempt declined this one: Better Work Tab's 1.6 assembly turned out far larger than its
About.xml description suggests — a full rule-builder engine, drag-drop, worklists, multiplayer
sync — and guessing its column-order API from that surface risked asserting something wrong about
someone else's mod. A narrower look at `Better_Work_Tab.Features.WorkColumnOrderManager` found the
actual mechanism is much smaller than the mod around it: `ApplyOrderToTable(PawnTableDef, List
<string>)` is a private method taking the table and the recorded order as plain arguments, rather
than reading them itself from live game state — callable directly by reflection, no `Current.Game`
needed for the reordering itself (only its two trailing notification calls need one, and those are
neutered by Harmony the same way `TheAccessTheModMakes` neuters an unrelated call to reach the one
under test).

`TheBetterWorkTabColumnOrder` loads the real `Better Work Tab.dll` from the local Workshop
subscription (skips cleanly if not installed), builds a `PawnTableDef` with three work columns and
one non-work column, applies a recorded order that only names two of the three work types, and
confirms: the non-work column is left alone, the two known types land in the recorded order, and
the type missing from that order — "created afterwards", in About.xml's words — goes last. Checked
for real discrimination, not a tautology: swapping the two names in the recorded order flips which
check fails, confirming the assertions read the actual reordering rather than a fixed expectation.

Unlike scenario 7, Work Studio owns no code path into Better Work Tab at all — this protects the
truth of the mod's own README/About.xml prose about the interaction, not a Work Studio regression.

  against a path this suite computes itself.

  TESTING.md.
